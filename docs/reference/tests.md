# Tests

Every file here is a distinct guarantee, which is why this page names them one at a time: knowing
_which_ test covers a rule is most of the value of having it.

Tests live in two places, and the split is by scope. A test about **one module** lives inside that
module. A test about **the system** — infrastructure, the kernel, the app shell, or a rule that
holds across every module — lives in `tests/`.

**Vitest** owns everything that runs in jsdom: pure functions, stores, composables, and single
components mounted with `@vue/test-utils`. **Cypress** owns everything needing a real browser — and
in this repo that means a real backend too, since the mock layer was retired in favour of the
paired backend's demo profile.

### What earns a test {#what-earns-a-test}

A documented rule gets a test when all three hold:

1. **A line of our own code enforces it today** — a branch, comparison, sort, constant, guard,
   emitted event, route registration or storage write, so a change to existing code can break it.
    - Skip a rule that holds **by absence** (no code path writes it, no second caller, no storage
      call) or **by construction** (a value read back from the server's answer, or a check the
      server makes and the client only renders). Breaking it means writing new code on purpose.
    - Exception: a security stop that a **dependency** provides (the router guard, Zod's strict
      parse) gets one learning test. Dependabot bumps dependencies weekly, unasked.
2. **A break would be silent** — nothing fails at build, no type error, no other suite goes red.
3. **Someone is hurt by the break** — a wrong price or total shown, data leaked into browser
   storage, an accessibility block for a user, a broken journey, a state or precedence rule, a
   promise to the server (retry and idempotency semantics included). A styling slip nobody can
   act on is not hurt.

How to build what passes:

- If a sweep already owns the family, extend the sweep in `tests/cross-cutting/`; do not add a per-view copy.
- Put the logic a test must see in a `.ts` file, not in a `.vue` script: Stryker mutates the
  first and never the second. Write the test in a suite Stryker runs (unit, cross-cutting or a
  co-located module spec). Cypress only when the claim needs a real browser and the real backend.
- Read [Mutation Testing](../build/mutation-testing.md) for what a surviving or `NoCoverage`
  mutant means.

## `tests/cross-cutting/` — rules that hold across every module

One file per architectural rule, asserted over every module at once. A new module is
covered the day it is added.

Module coupling is not among them: which module may import which is a generated ESLint rule
(`dependsOn` in each `module.yaml`, read by `eslint.config.ts`), enforced at the import on every `npm run lint` rather than
reconciled against a manifest field here. See
[Strategic DDD](../understand/strategic-ddd.md) §2 and §4.

## Co-located module tests

| Pattern                                       | What it is                                                                                                                                                                                                                                                                                                              | Read next                                                    |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `src/modules/*/tests/*.spec.ts`               | The module's own unit suites — one per subject, most commonly its store and its routes.                                                                                                                                                                                                                                 | [Unit Testing](../build/unit-testing.md)                     |
| `src/modules/*/tests/e2e/*.cy.ts`             | Browser specs that belong to one domain, including its slice of the accessibility sweep.                                                                                                                                                                                                                                | [Live E2E](../build/live-e2e.md)                             |
| `src/modules/*/tests/lighthouse.ts`           | The Lighthouse cases the module contributes (`lighthouseCases`): routes the nightly audit loads on a phone profile.                                                                                                                                                                                                     | [Lighthouse](../build/lighthouse.md#cases-live-with-modules) |
| `src/modules/*/tests/e2e/__snapshots__/*.png` | That domain's own visual baselines, one per viewport and theme (`<name>.<viewport>[.dark].png`). Most of the repo's baselines live here rather than under `tests/e2e/visual/`, for the same reason its specs do: a screenshot of the orders table belongs to `orders`, and `rm -rf` on the module should take it along. | [Visual Regression](../build/visual-regression.md)           |
