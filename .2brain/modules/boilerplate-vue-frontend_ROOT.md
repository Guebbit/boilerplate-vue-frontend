# / (repository root)

## Purpose

The repository root is the build, contract, and deployment shell for **boilerplate-vue-frontend** — a Vue 3 + TypeScript SPA that is contract-first (OpenAPI for REST, AsyncAPI for events), modular by domain, and designed to run with or without a live backend. This level owns the project manifest, the generated and hand-written contract files, the Docker deployment pipeline, the documentation site configuration, cross-cutting quality gates (lint, mutation testing, CI tooling), and the public static assets that ship with every build.

## Key parts

- **Project manifest & build config** — `package.json`, `eslint.config.ts`, `orval.config.ts`, `stryker.config.json`, `spectral.yaml`, `release-please-config.json`, `cypress.config.ts`. Together they define the task surface, enforce the architectural tier ladder and module boundaries at lint time, drive codegen from specs, gate mutation-test quality, lint the OpenAPI contract, and wire automated releases.
- **Contract sources & generated artifacts** — `openapi.yaml` and `asyncapi.yaml` are the bundled, canonical specs. The `contracts/` directory holds every generated consumer-facing file: typed REST types (`contracts/rest/index.ts`), Zod schemas (`contracts/rest/schemas.zod.ts`), error codes, route tables, permission actions, and AsyncAPI event types. These are regenerated by `npm run gen:*` commands and must not be hand-edited.
- **Deployment & runtime config** — `docker-compose.yml` (dev: Vite + VitePress), `docker-compose.production.yml` (prod: static bundle in nginx), `docker/Dockerfile.production`, and the two entrypoint hooks under `docker/docker-entrypoint.d/` that emit `config.js` and `security.txt` from environment variables at container start.
- **Documentation site** — `docs/.vitepress/config.mts` and `docs/.vitepress/theme/index.ts` configure the VitePress site (navigation, sidebar, Mermaid zoom). `docs/tools/` holds how-to pages for live e2e and visual regression.
- **Cross-cutting test guards** — `tests/cross-cutting/` contains Vitest specs that enforce structural invariants no single-module test can catch: a11y sweep coverage, backend module pairing, badge accessibility, and destructive-dialog naming.
- **Static assets & boot shell** — `index.html` is the SPA entry point (splash, PWA metadata, config script). `public/` holds favicons, brand SVGs, and the no-image placeholder.
- **Project documentation** — `README.md`, `INSTALL.md`, `SECURITY.md`, and `CLAUDE.md` cover onboarding, external prerequisites, vulnerability reporting, and AI-assistant coding conventions.

## How it connects

- **`src/` and all `src/modules/*`** — The root's contract files (`contracts/rest/*`, `contracts/asyncapi.generated.ts`, `contracts/permission-actions.ts`, `contracts/authorization-keys.yaml`) are the typed interfaces every module's API client, route guards, and event handlers import. The ESLint tier ladder defined in `eslint.config.ts` is the rule set those modules are linted against. The `cypress.config.ts` Node tasks provide the server-side helpers each module's e2e specs call.
- **`src/infrastructure/http/`** — Consumes the generated `contracts/rest/index.ts` (axios functions) and `contracts/rest/schemas.zod.ts` (runtime validation) to build the shared API client layer; the root's `orval.config.ts` is what keeps those files in lockstep with `openapi.yaml`.
- **`scripts/` and `scripts/e2e/`** — The `package.json` task scripts and `cypress.config.ts` invoke these scripts; the `docker-entrypoint.d/` hooks and `docker-compose*` files are the production counterparts to what those scripts do locally.

## Where to start

1. **`README.md`** — Two minutes of context on what the project is, its contract-first philosophy, and the demo-vs-live run modes.
2. **`contracts/rest/index.ts`** (generated, ~read-only) — Skim the exported types and function signatures to see the shape of the API surface every module talks to; it is the single file that tells you "what the frontend can ask the backend to do" in one glance.

- `asyncapi.yaml` — Generated AsyncAPI 3.0.0 specification that bundles all real-time and event-driven contracts (SSE streams and outbound webhooks) from individual module fragments into a single, canonical document. It is the single source of truth for event names, payload shapes, and channel identifiers, produced from `asyncapi.yaml` by `npm run gen:asyncapi`. It exists so that producers, consumers, and the SSE layer all agree on wire formats without hand-maintained duplication.
- `contracts/authorization-keys.yaml` — The single, canonical catalogue of every permission rule and the action vocabulary it uses. It is a **generated bundle**: `npm run authorization:bundle` splices one fragment per owning module (`src/modules/<name>/authorization.yaml`) plus a root residual for `core` rules. It is committed byte-for-byte identical in both backend repositories so that the two codebases share one authorization source of truth without either repo's formatter mutating it.
- `contracts/permission-actions.ts` — Generated contract file that defines the closed set of valid permission actions in the system. It exists as a single source of truth for TypeScript consumers (frontend, backend, tests) so that every action string used in permission checks is type-checked against the same list. Regenerate it rather than editing by hand.
- `contracts/rest/error-codes.ts` — Auto-generated enumeration of every error code declared in the OpenAPI contract. It exists as the single typed reference for all REST error codes so that consumers (client SDKs, error-handling middleware, test suites) can match against a known set rather than raw strings. Adding a new code is additive and never a breaking change.
- `contracts/rest/index.ts` — Auto-generated (orval v8.20.0) TypeScript type definitions for the project's stable OpenAPI REST contract. It is the single source of shared types — scalar aliases, envelope shapes, error structures, and domain interfaces (User, Locale, Language, Health) — that both the API client layer and feature modules import to stay type-safe against the server. **Do not edit manually.**
- `contracts/rest/operation-modules.ts` — Auto-generated lookup table that maps every `@api` function name to the backend module string that owns the corresponding OpenAPI operation. It exists so consumers (routing, auth scoping, analytics attribution, tests) can resolve "which module does this operation belong to?" without re-parsing the spec.
- `contracts/rest/routes.ts` — Auto-generated route table for the REST API contract. It is produced by `npm run gen:api` from `openapi.yaml` and provides a flat, typed list of every HTTP operation (method + path pattern) along with the schema names the backend must validate. It serves as the single source of truth the response-validation layer and schema-lookup machinery iterate over.
- `contracts/rest/schemas.zod.ts` — Auto-generated (orval v8.20.0) Zod schemas that validate the request and response shapes for the Boilerplate REST API's operational endpoints (health, liveness, readiness, `security.txt`) and its locale/internationalization surface (listing, creating, replacing languages; listing translation apps; fetching the API's own message dictionary). Exists so that server handlers and any client-side validation share a single, type-safe contract derived from the OpenAPI spec.
- `cypress.config.ts` — Cypress configuration for all browser-based e2e suites. The same spec set runs under a **demo** or **live** profile, selected at runtime via the `liveProfile` flag rather than via separate configs.

It exists so a deploy command is one `docker compose up` invocation rather than a hand-rolled build-and-serve pipeline.

Placing the logic at runtime (like `config.js`) ensures a fork never ships a stale or foreign contact address baked into the image.

- `tests/cross-cutting/a11y-coverage.spec.ts` — A Vitest spec that enforces a11y coverage structurally: it reads every module's `routes.ts` and its co-located `a11y.cy.ts` sweep, then asserts that every declared route is visited by the sweep (and vice-versa). It does **not** run axe or open a browser — it catches the absence of a sweep, which no in-Cypress assertion could report because a missing spec simply never runs.
- `tests/cross-cutting/backend-pairing.spec.ts` — A Vitest spec that enforces cross-repository pairing between this repo's enabled modules and their counterparts in `boilerplate-node-backend`. It exists because nothing in a frontend build fails when the backend renames, splits, or adds a module — the two module maps drift silently until someone is lost. Living in a spec (not prose docs) means a broken pairing fails the test gate rather than just going stale on a wiki page.
- `tests/cross-cutting/badge-name.spec.ts` — Static-analysis guard that every `<v-badge>` in shipped Vue components carries an accessible name (`label`, `aria-label`, or `aria-hidden`). A missing name is visually invisible and uncatchable by lint, so the invariant is pinned here rather than enforced by a shared component (which would only cover two of the four badge surfaces and still miss the icon-button case).
- `tests/cross-cutting/destructive-confirm-naming.spec.ts` — Cross-cutting guard test that enforces a single convention: every destructive (`color: 'error'`) confirm dialog must name its target via a `t(key, { … })` interpolation param, so a visitor can tell *which* row they are about to delete. It exists to prevent new components from regressing to bare "delete this item?" wording.
- `tests/cross-cutting/entry-chunk-budget.spec.ts` — Guards against the production entry chunk (the single JS file every visitor downloads before any other code runs) growing past a raw-byte ceiling. It performs a real `vite build` into a throwaway temp directory and asserts both a size budget and that the large Zod schema contract chunk remains code-split (i.e., not referenced by the HTML shell at parse time).
- `tests/cross-cutting/form-idiom.spec.ts` — Enforces a single form idiom across every `.vue` component in `src/modules` that calls `useStructureFormValidation`. It statically scans source text (via the TypeScript compiler API) to verify three rules: every call supplies `revalidateOn`, `invalidFieldSelector`, and `onInvalid`; no view declares its own `showErrors` ref alongside the composable's `showFormErrors`; and page forms (outside `components/`) pass a `formElement`. The file exists because thirteen real forms proved the toolkit's defaults are not sufficient on their own — missing options cause silent accessibility failures (no focus move on invalid submit) that no unit test would catch.
- `tests/cross-cutting/journey-headers.spec.ts` — Cross-cutting integration test that verifies every journey spec under `tests/e2e/specs/journeys/` declares a valid `// requires-module:` header (or `none`). Without this header, `npm run demo:remove` would strip the referenced module but leave the journey spec orphaned, causing a later failure. This spec runs the header-checker against the real repo tree (the checker's own unit tests live in `tests/unit/scripts/demo/demo-remove-tests.spec.ts`).
- `tests/cross-cutting/module-coupling.spec.ts` — Enforces that a module's `@api` (generated REST client) calls target only backend modules declared in its coupling (`MODULE_EDGES`). This closes a gap ESLint boundary rules leave open: a module importing another module's backend operation through the `@api` barrel without declaring the edge.
- `tests/cross-cutting/module-file-shapes.spec.ts` — Enforces that every file inside a `src/modules/*` folder matches a named, catalogued shape (`module.ts`, `routes.ts`, `store.ts`, `views/*.vue`, etc.). Any file that matches no entry in the catalogue fails the test by name, making the module vocabulary an enforced invariant rather than a convention. It also enforces per-module exclusivity (`onlyIn`) for shapes reserved to a single domain.
- `tests/cross-cutting/module-groups.spec.ts` — Enforces the **completeness** half of the foundation | shop module-axis guarantee: every enabled module must have a `MODULE_GROUPS` label, no stale labels may linger for disabled modules, and both group values must be in active use. It pairs with the `foundation-may-not-import-shop` ESLint rule (which enforces *direction*) to make the axis a deliberate, non-omissible choice when adding modules.
- `tests/cross-cutting/mutate-scope.spec.ts` — Guarantees that the `mutate` globs declared in `stryker.config.json` still resolve to at least one real file. A glob that silently matches nothing (e.g. after a directory rename) would stop measuring code without any error; this test turns that quiet gap into a red test run.
- `tests/cross-cutting/mutation-safe-imports.spec.ts` — Static guard that every template-literal `import(...)` and `import.meta.glob(...)` specifier inside the Stryker mutation scope is preceded by a `// Stryker disable` directive. Without it, Stryker's template-literal mutator would replace the specifier with an empty string, causing the instrumented build to fail during the dry-run phase with an unhelpful sandbox-path error before a single mutant is evaluated.
- `tests/cross-cutting/page-window-density.spec.ts`
- `tests/cross-cutting/published-language.spec.ts` — A cross-cutting architectural test that enforces the rule "a module publishes exactly what a sibling imports." It scans every module's `index.ts` barrel against all source-file imports and fails if any export has no sibling consumer or if a barrel exists for a module nobody imports. It exists to catch the slow rot of barrels accumulating dead exports that outlive their reason.
- `tests/cross-cutting/registry.spec.ts` — A cross-cutting spec that iterates the enabled-module registry and asserts invariants every module must satisfy—navigation/route integrity, i18n namespace ownership, and translation-key liveness—without ever naming a specific domain. Deleting any module simply reduces the number of cases exercised; the file never hardcodes a module name, keeping it valid regardless of which modules are present.
- `tests/cross-cutting/route-name-coupling.spec.ts` — Detects cross-module route-name references (e.g. `router.push({ name: 'SiblingRoute' })`) that lack both a `MODULE_EDGES` coupling and a runtime guard (`hasRoute` / `linkIfRouted`). Because route names are plain strings invisible to import-based boundary rules, this spec scans **source text** to catch the coupling that `eslint.config.ts` cannot see, preventing a deleted module from causing a runtime `vue-router` throw.
- `tests/cross-cutting/schemas-i18n.spec.ts` — Verifies the cross-cutting contract that Zod schemas with thunked error messages (`{ error: () => translate('…') }`) resolve in the active locale at parse time, and that `useStructureFormValidation`'s `revalidateOn` option re-translates errors already rendered on screen after a locale switch. Uses a deliberately invented schema and synthetic locale dictionary so the spec survives deletion of any real domain module.
- `tests/cross-cutting/sitemap-document.spec.ts` — Serves as both the **test** and the **generator** for the route table embedded in `docs/theory/sitemap.md`. It asserts that the markdown table between the `<!-- sitemap:start -->` / `<!-- sitemap:end -->` markers exactly matches the routes contributed by `enabledModules`, and (when `UPDATE_SITEMAP=1` is set) rewrites that block in place. It lives as a spec rather than a script because the route records lazy-load `.vue` views through `@/` aliases, which only the Vitest/Vite pipeline can resolve.
- `tests/cross-cutting/store-location.spec.ts` — Enforces a file-layout convention for Pinia stores: every module must declare its stores in exactly one of two shapes — `store.ts` (single store) or `stores/*.ts` (multiple stores) — and never both. It scans `src/modules` for any file containing a `defineStore(` call and asserts the file sits in a permitted location, so that path-based tooling and readers have one unambiguous answer to "where is this store?"
- `tests/e2e/fixtures/not-an-image.txt` — not an image, on purpose

Module-owned routes have their own sweeps under `src/modules/<name>/tests/e2e/a11y.cy.ts`; this file exists so that deleting a domain does not orphan a11y coverage, and so shared chrome is audited once rather than duplicated per module.
- `tests/e2e/specs/commerce.cy.ts` — End-to-end Cypress spec that walks the full commerce arc: a customer buys a product, exercises the payment panel (declined card → 3-D Secure challenge → successful payment), cancels a paid order; then an admin moves that paid order to processing, ships it through the shipment panel, marks it delivered, and verifies the inventory ledger recorded the receipt with the correct counters. The two `it` blocks are deliberately self-contained (each builds its own state, never relies on a prior test's store).
- `tests/e2e/specs/consent.cy.ts`
- `tests/e2e/specs/harness.antibot.cy.ts`
- `tests/e2e/specs/harness.cy.ts` — Meta-spec that validates the journey-harness infrastructure itself (`cy.travel`, session mode, persona/staff accounts, second device, signed webhooks, webhook sink, job lever, and browser helpers) so that journey specs can rely on those primitives without re-proving them. Each capability is exercised once here; if it breaks, the failure points at the harness rather than at whichever journey spec happened to run first.
- `tests/e2e/specs/journey.cy.ts` — End-to-end test that walks the full customer lifecycle in one continuous session: a guest browses and hits the sign-in wall, then an authenticated user filters, buys, checks out, cancels, and verifies the shelf's stock count recovers. After login the test navigates exclusively through in-app links and buttons (no `cy.visit`) to prove state survives across pages without a full reload.
- `tests/e2e/specs/journeys/ac1-lost-my-phone.cy.ts` — Cypress end-to-end journey test for acceptance criterion AC1 ("I lost my phone"). Verifies the full backup-code sign-in flow: a code is single-use, a second attempt with the same code is rejected, a different code still works, and regenerating the code set invalidates every old code (used or unused) while a new code signs in successfully.
- `tests/e2e/specs/journeys/ac11-i-moved-house.cy.ts` — End-to-end test for the "I moved house" acceptance criteria.
