# src/modules/account/tests/e2e/a11y.cy.ts

## Purpose

Declares the list of routes and in-page states that the account module exposes to the accessibility sweep. It does not contain audit logic; it only names *what* to audit and *how to reach* each state (via a route string or a `prepare` callback). Co-located with the account module so that deleting the module removes its a11y coverage automatically, and so that `tests/cross-cutting/a11y-coverage.spec.ts` can verify no routed module is left without one.

## Key elements

- **`UNISSUED_TOKEN`** – A constant token string (`'a-token-nobody-issued'`) appended to the `#token` fragment of every confirm/setup/restore route. Simulates the state a visitor with an expired or never-received email link would see: the form renders but submit would fail.
- **`sweepA11y('account — guest', …)`** – The first sweep call. Audits unauthenticated pages: login, signup, password-reset (+ confirm), account-setup/restore, email-verify/change confirm + undo, OAuth callback error, plus prepared variants (dark theme, form-submitted-empty, 2FA challenge, deletion-restore offer).
- **`sweepA11y('account — signed in', …, 'user')`** – The second sweep call (runs as the demo `user`). Audits authenticated pages: profile, account-export download (normal, no-export, export-gone), and two modal dialogs (address add, authenticator enrolment).
- **`prepare` callbacks** – Inline Cucumber-style steps that drive the UI to a specific state before the a11y snapshot is taken (e.g., clicking submit to surface validation errors, opening a dialog, intercepting API responses to simulate 404s).

## Relationships

- **`tests/support/e2e/a11y-sweep.ts`** – Provides `sweepA11y`, the function that iterates the route list and runs the actual axe-core (or equivalent) audit on each entry. This file is purely declarative input to that function.
- **`tests/support/e2e/scenario.ts`** – Provides `seedAccount`, used in the 2FA and deletion-restore `prepare` blocks to retrieve the demo user's email/password so the test can sign in through the real form flow.

## Notes

- **Cold-visit pitfall:** The 2FA challenge and deletion-restore states live in Pinia memory, not the URL. A bare `cy.visit('/en/login/2fa')` bounces back to the login page. Both `prepare` blocks therefore perform a *real* sign-in (enroll → logout → re-login, or API-delete → re-login) to reach the state organically.
- **Token pages:** Using `UNISSUED_TOKEN` is intentional—it exercises the "expired link" rendering path, which is the state a real visitor would hit. It does *not* exercise the post-submit success or failure branches.
- **OAuth success is skipped:** The success callback redirects immediately and renders no page of its own; only the error state (`?error=access_denied`) is included.
- **Account-export 404 scenario:** The "export gone" case requires two separate intercepts (status endpoint returns `ready`, file endpoint returns 404) because that is the only way the UI shows the download button enabled *and* then errors.
