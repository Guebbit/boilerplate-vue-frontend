# contracts/rest/operation-modules.ts

## Purpose
Auto-generated lookup table that maps every API operation name to the backend module that owns it. It exists so that tooling (routing, auth scoping, module-coupling tests) can resolve "which module is responsible for this endpoint" without re-parsing the OpenAPI spec at runtime.

## Key elements
- **`OPERATION_MODULES: Record<string, string>`** – The sole export. A flat map of ~190 operation identifiers (e.g. `checkout`, `createProduct`, `shipOrder`) to a short module slug (e.g. `'cart'`, `'products'`, `'delivery'`). Module slugs include: `account`, `addresses`, `antibot`, `api-keys`, `audit-logs`, `cart`, `delivery`, `feedback`, `invoicing`, `inventory`, `locales`, `observability`, `orders`, `payments`, `products`, `returns`, `users`, `webhooks`, `wishlist`.

## Relationships
- **`tests/cross-cutting/module-coupling.spec.ts`** – Consumes `OPERATION_MODULES` to assert that each operation is assigned to exactly one module and to detect unintended cross-module coupling in the codebase.

## Notes
- **Do not edit.** The file is regenerated by `npm run gen:api` from `openapi.yaml`. Any manual change will be overwritten on the next generation run.
- The mapping is a simple `name → slug` pair with no further metadata (no HTTP method, path, or version info). If two operations share a name across different specs they would collide here; currently all keys are unique.
- Module slugs are free-form strings, not enum members—there is no compile-time guarantee they correspond to an actual directory or package.
