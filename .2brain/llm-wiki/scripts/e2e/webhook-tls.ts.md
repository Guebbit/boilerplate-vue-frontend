# scripts/e2e/webhook-tls.ts

## Purpose

Centralises the loading of the demo webhook sink's TLS material (a test CA, a leaf cert for `127.0.0.1`, and its private key) into a single read at module-evaluation time. It exists so that the sink (`webhook-sink.ts`) and the tester (`webhook-tester.ts`) share one source of truth for the PEM files rather than each reading them independently.

## Key elements

- **`TLS_DIRECTORY`** – module-private constant; resolves to `<this-file-dir>/tls` via `import.meta.dirname`.
- **`readPem(name)`** – module-private helper; reads one PEM file from `TLS_DIRECTORY` and returns a `Buffer`.
- **`WEBHOOK_SINK_TLS`** (exported, `as const`) – the single public export. An object with `ca`, `cert`, and `key` (all `Buffer`s) shaped to spread directly into `node:https` server options.

## Relationships

- **`scripts/e2e/webhook-sink.ts`** – imports `WEBHOOK_SINK_TLS` to configure its HTTPS server on loopback.
- **`scripts/e2e/webhook-tester.ts`** – imports `WEBHOOK_SINK_TLS` (specifically the `ca`) to trust the sink's leaf when making outbound HTTPS calls.
- **`tests/unit/scripts/e2e/webhook-sink.spec.ts`** / **`tests/unit/scripts/e2e/webhook-tester.spec.ts`** – exercise the sink and tester respectively; TLS material flows through them indirectly via the shared export.

## Notes

- The three PEM files under `tls/` are **copied from the backend** by `sync:frontend` and verified by `check:spec-identity`. They are regenerated by the backend's `npm run scenario:tls`. **Do not edit them in this repo.**
- The leaf private key is committed on purpose; it is only meaningful for `127.0.0.1` and carries no production trust.
- The files are read synchronously at import time (`readFileSync`). This means the `tls/` directory must already be populated before any code imports this module (i.e., after `sync:frontend` has run).
- The comment block explicitly states the file is kept separate so that "serves" and "reads" share one reading—do not inline the reads into the sink or tester.
